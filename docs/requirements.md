# Zero 需求清单（按优先级）

> 来源：Zero 学习陪伴场景作业（题目一架构设计 + 题目二 Agent 对话服务实现）。
> 整理日期：2026-11-21。本清单是题目一设计与题目二实现的共同依据。

## 优先级定义

| 级别 | 含义 |
|---|---|
| **P0** | 硬性验收项：缺失则作业不达标（题目二所有"必须"项 + 题目一五个设计问题 + 交付物） |
| **P1** | 要求内但可简化/预置实现，或显著降低验收风险的支撑项 |
| **P2** | 选答、加分项，或题目二明确豁免实现、但题目一必须设计的能力 |

---

## 一、P0：对话接口与持久化（题目二 §1）

| ID | 需求 | 验收要点 |
|---|---|---|
| A1 | `POST /conversations/{id}/messages` | 接收用户消息 → 调真实模型 API → SSE/分块流式返回 → **明确的完成或失败信号**（结束事件/错误事件） |
| A2 | `GET /conversations/{id}/messages` | 确定顺序返回完整历史；每条消息可识别**所属轮次 + 执行状态**；分页可选（P2） |
| A3 | 消息与轮次状态持久化 | 服务重启后历史与状态仍可正确读取（测试 T1） |
| A4 | **断线语义定义并实现** | 明确：断开后是否继续生成、部分回复是否落库、重读历史看到什么；写入 README（测试 T2 按此断言） |
| A5 | 轮次（turn）作为一等实体 + 状态机 | 用户消息先落库再执行；状态如 pending/running/completed/failed/interrupted；模型调用、工具调用、回复、状态全部关联到 turn_id |
| A6 | 每轮审计记录 | 计划策略+版本、实际策略+版本、是否回退+原因、执行状态（题目二 §2 明确列出） |

## 二、P0：Agent 执行框架与策略（题目二 §2）

| ID | 需求 | 验收要点 |
|---|---|---|
| B1 | 公共执行器 | 统一负责模型调用循环、工具执行循环、流式输出、结果持久化；与策略解耦 |
| B2 | 策略接口 | 每轮由策略决定：①给模型的指令 ②本轮历史与上下文 ③允许的工具。输入/输出/职责边界在题目一说明 |
| B3 | ≥2 种策略 | 讲解优先、练习优先 |
| B4 | 注册/配置切换机制 | **新增策略不改对话存储、HTTP 接口、公共执行流程**（扩展性验收核心） |
| B5 | 策略版本管理 | 版本号随每轮审计落库；题目一需说明版本回滚机制 |
| B6 | 故障回退 | 策略**构建本轮配置阶段**异常 → 自动退回默认策略；明确回退适用阶段；默认策略也失败 → 轮次标记 failed + 明确失败信号，用户消息保留 |
| B7 | ≥1 个工具 | 预置材料片段查询；留存一次**真实模型发起 tool call → 接收结果 → 继续生成**的运行示例 |
| B8 | 上下文构建模块 | 完整历史（权威）≠ 模型实际上下文（窗口/摘要/检索片段）；本轮上下文可追溯；题目一说明长对话（上百轮）与大材料（500 页）处理方案 |

## 三、P0：并发与故障一致性（题目一 §3 + 题目二测试）

| ID | 需求 | 验收要点 |
|---|---|---|
| C1 | 同一对话并发写入串行化 | 多进程安全（DB 锁/每对话队列）；不丢失、不重复；成功轮次的用户消息与回复**成对、有序、不与其他轮次交错**（测试 T3，两进程或两独立 DB 连接验证） |
| C2 | 请求重试幂等 | 题目一必答（如 client_msg_id 去重）；实现建议做，成本低（P1 实现） |
| C3 | 故障后一致性 | 模型调用失败 → 轮次 failed 可重试；服务重启 → 孤儿 running 轮次被恢复或标记，历史与执行状态一致 |
| C4 | 单机多进程部署约束 | 共享数据库为权威源，进程内不持有权威状态；这是题目一所有并发设计的前提 |

## 四、P0：自动化测试（题目二 §4，模型相关必须用真实 API）

| ID | 场景 | 验收要求 |
|---|---|---|
| T1 | 持久化与重启 | 写入后重启服务，历史+轮次状态正确读取 |
| T2 | 流式中断 | 输出中途主动断连，最终落库的消息/部分回复/状态符合 A4 定义的语义 |
| T3 | 同对话并发写入 | 两请求并发，完成后不丢不重、成对有序不交错 |
| T4 | 策略切换与故障回退 | 切换后实际策略变化；故障注入触发异常 → 默认策略接管，审计记录准确反映回退 |
| T5 | 评估重复执行 | 固定输入配置跑两次，用例均执行、逐轮记录完整、检查正确汇总、两次运行可区分对比 |

## 五、P0：基础评估（题目二 §3）

| ID | 需求 | 验收要点 |
|---|---|---|
| E1 | 3–5 组固定多轮用例 | 含"答错"场景；用例文件版本化固定 |
| E2 | 控制变量 | 除策略外，模型、调用参数、初始数据、输入一致；两策略从**独立初始会话**运行 |
| E3 | 逐轮记录 | 执行信息（用例/轮次/模型标识/调用参数/策略版本）+ 资源性能（输入/输出 token、耗时、工具调用次数）+ 预定义检查项及结果 |
| E4 | 自动行为检查 | 如：练习优先首轮是否提问；答错后是否解释；是否只调用了本轮允许的工具；（可加）讲解优先是否先讲解再出题 |
| E5 | 输出物 | 逐轮评估记录 + 两策略对比表 + 差异简述 |
| E6 | 可重复执行 | 同配置完整跑**两次**并留档；run_id 区分；记录完整可追溯（不要求结果完全一致） |

|---|---|---|---|

## 九、题目二倒逼题目一必须先拍板的设计决策

写设计文档前先定下这 8 个决策，每个都直接对应上面的 P0 验收项：

1. **轮次模型与状态机**（A5/A6/C3）：turn 是一等实体，所有执行产物挂 turn_id → 决定表结构。
2. **断线语义**（A4/T2）：生成与连接解耦、后台继续生成并保存部分/完整回复（推荐），还是断连即取消 → 决定执行器任务模型，测试 T2 按此断言。
3. **并发串行化机制**（C1/T3）：DB 行锁/advisory lock 还是每对话队列；轮次序号如何分配 → 多进程下"成对有序不交错"的唯一保障。
4. **权威源分层**（A3/B8/G2）：消息/轮次/审计以 DB 为权威；材料原文权威、解析与索引可重建 → 决定删除与恢复逻辑。
5. **策略 = 纯规划器**（B2/B4/B6）：策略只产出 TurnPlan（指令+上下文+允许工具），不调模型、不写库；回退只发生在 plan 构建阶段 → 保证新增策略零改动公共层。
6. **策略注册表 + 版本化配置**（B5/B6/G7）：切换、回滚、计划 vs 实际审计都由此支撑。
7. **上下文构建器独立成模块**（B8）：完整历史与模型上下文分离，长对话窗口/摘要、大材料检索都在此收敛。
8. **每轮审计即评估数据源**（A6/E3）：token、耗时、工具次数、策略版本在执行时落库，评估脚本直接读 → 执行与评估共用一套记录，天然可追溯。

**建议推进顺序**：先定第九节 8 个决策 → 产出题目一架构图 + 一页说明 → 实现按 存储/轮次模型 → 执行器+SSE → 策略+回退+工具 → 五个测试 → 评估两跑 → README/交付物。
